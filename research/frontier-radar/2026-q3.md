## FR-01: Context Engineering and Compaction

### Core problem

The harness must decide what enters the model context, what remains durable, what
can be discarded, and how to recover task-critical state after compression.

### Current evidence

- Long-context models do not uniformly use relevant information by position;
  relevant details near the middle can be missed.
- Prompt-compression research shows possible token reduction, but compression is
  model- and task-sensitive.
- DeepSeek Harness uses an append-only session log, durable surface replacement,
  tool-result pruning, threshold-based compaction, and overflow-triggered retry.
- Claude Code uses several ordered reductions before full compaction and
  explicitly restores selected file, plan, skill, and subagent state afterward.

### Engineering readiness

High for a first deterministic projection and compression policy; medium for
generalizing one threshold or compressor across models and workloads.

### Harness implication

Compaction is not merely summarization. It is a state-projection and recovery
problem. The minimum durable contract is the task objective, active plan,
changed files, verification state, unresolved work, and indivisible tool-call
relationships.

### Failure modes

- A summary drops a safety constraint, user requirement, or failed verification.
- A tool call is split from its result or an unstarted call is replayed.
- File observations become stale after compaction or resume.
- One compressor is tuned on one model or language mix and regresses elsewhere.
- Prompt-prefix changes cause cache loss on every turn.

### Horizon and probe

Primary horizon `H1`; some adaptive compression remains `H2`.

Probe: yes. Use fixed tasks that force context pressure, interrupted tool calls,
resume, and post-compaction verification. Compare structured projection against
plain summarization. Stop if task-success or safety evidence regresses.

## FR-02: Durable Memory

### Core problem

Across sessions, the system may need to retain stable preferences, project
facts, decisions, and corrections without confusing old or superseded state with
current repository truth.

### Current evidence

- MemGPT frames context limits as a multi-tier memory-management problem.
- LongMemEval evaluates extraction, multi-session reasoning, knowledge updates,
  temporal reasoning, and abstention.
- The updated LongMemEval repository now points to a separate agentic-context
  v2 effort, showing that the evaluation boundary is still moving.
- DeepSeek Harness has durable sessions and project instructions, but the
  inspected L4 atlas does not establish an autonomous long-term memory system.
- Claude Code combines instruction/memory files, nested attachments, and a
  feature-gated session-memory compaction path.

### Engineering readiness

High for explicit project instructions; medium for retrieval-backed memory;
lower for autonomous writes without a lifecycle contract.

### Harness implication

Project instructions and session facts are different classes of state.
Automatic memory should not be accepted as a generic improvement without a
lifecycle for provenance, supersession, retrieval, correction, and deletion.

### Failure modes

- Stale preferences override current user instructions.
- Cross-project or cross-user memory leaks.
- Retrieved memories lack source or timestamp and cannot be audited.
- The system confidently recalls superseded facts instead of abstaining.
- Memory writes amplify prompt injection or untrusted repository content.

### Horizon and probe

Primary horizon `H2`; project instruction loading is already `H1`.

Probe: offline only. Use a bounded benchmark to compare no memory, explicit
project files, and retrieval-backed memory. No P0 memory product is implied.

## FR-03: Planning and Replanning

### Core problem

The runtime needs an explicit way to represent intended work, expose progress,
revise a plan when evidence changes, and avoid treating a written plan as proof
that work was completed.

### Current evidence

- ReAct interleaves reasoning and actions with an environment.
- PlanBench tests planning and change reasoning separately from common-sense
  retrieval, exposing planning as a distinct capability.
- The inspected DeepSeek Harness runtime does not expose a plan state as a
  first-class session object in the L0-L4 evidence.
- Claude Code preserves plan state across full compaction, indicating that plan
  state can be operationally useful in a long coding task.

### Engineering readiness

High for a small durable plan object; medium for reliable replanning; lower for
search-based planning as a production runtime default.

### Harness implication

Start with a small, durable plan object and explicit status transitions. Do not
assume a hidden chain-of-thought or a static task list is a reliable runtime
mechanism.

### Failure modes

- The plan becomes stale after repository discovery.
- The model reports a step complete without execution evidence.
- Replanning loops or expands indefinitely.
- A plan duplicates the transcript and becomes another source of truth.
- Planning quality is inferred from one benchmark or one model family.

### Horizon and probe

Primary horizon `H1` for explicit plan state; `H2` for planner search,
uncertainty handling, and Plan mode.

Probe: yes. Persist one plan event per revision, keep it separate from model
reasoning, and test status after tool failure and resume. Stop if the plan adds
state without improving completion or recovery.

### Evidence

Detailed facts, versions, and unresolved questions:
[`mechanism-notes.md#fr-03-planning-and-replanning`](../landscape/papers/mechanism-notes.md#fr-03-planning-and-replanning)

## FR-04: Verification and Completion Gates

### Core problem

The harness needs an auditable distinction between "the agent says it is done"
and "the required result was verified under stated conditions."

### Current evidence

- Process-supervision research shows intermediate verification can improve
  multi-step reasoning, but the evidence is primarily reasoning-model training,
  not a coding-runtime guarantee.
- SWE-bench standardizes issue-to-patch evaluation in real repositories and uses
  reproducible environment execution.
- SWE-bench Verified is a 500-task subset curated for solvability.
- Both inspected harnesses can execute tools and preserve results, but neither
  provides a universal guarantee that the final test run covers the requested
  change.

### Engineering readiness

High for recording command evidence and testing deterministic acceptance; medium
for semantic acceptance and non-code tasks.

### Harness implication

Verification should be a runtime-visible evidence contract. A completion record
should identify commands, exit status, relevant output, changed files, and
remaining uncertainty. Model self-critique can be an additional signal, not the
sole verifier.

### Failure modes

- The agent runs a narrow test and presents it as full verification.
- A test passes before the final edit or against a stale process.
- The agent modifies or bypasses the test that defines acceptance.
- A non-code change has no deterministic verifier.
- The final message omits failed, skipped, or unavailable checks.

### Horizon and probe

Primary horizon `H1`.

Probe: yes. Make verification evidence part of the fixed-task acceptance record
and test adversarial cases such as changing only tests or passing before the
final edit. Stop if the gate blocks normal work without reducing false
completion.

### Evidence

Detailed facts, versions, and unresolved questions:
[`mechanism-notes.md#fr-04-verification-and-completion-gates`](../landscape/papers/mechanism-notes.md#fr-04-verification-and-completion-gates)

## FR-05: Tool Learning and Function-Calling Evaluation

### Core problem

Tool reliability is a joint property of the model, schema, prompt representation,
runtime validation, and execution environment. The harness must not attribute a
model failure to the tool layer, or vice versa.

### Current evidence

- Toolformer trains a model to decide when to call APIs and how to use results.
- Gorilla combines model fine-tuning with retrieval for API usage.
- BFCL V4 evaluates executable function calls, multi-step behavior, web search,
  agentic memory, and format sensitivity.
- DeepSeek Harness has a strong runtime tool contract with schemas, policies,
  scheduling, result normalization, and durable call/result relations.
- Claude Code has a broader capability contract spanning permissions, UI,
  telemetry, concurrency, and model serialization.

### Engineering readiness

High for schema stability and evaluation; medium for model-specific adaptation;
lower for training or learned runtime policy.

### Harness implication

Tool learning affects model qualification more than it justifies a custom
training program. The first useful runtime work is stable schemas, negative
examples, format variation, permission semantics, and model-specific evaluation.

### Failure modes

- A model overfits one JSON/tool-call format and fails under another.
- Benchmarks reward parsing while runtime execution or safety fails.
- Schema changes invalidate prompt caches or learned behavior.
- The harness hides tool errors and prevents measurement.
- A learned policy is treated as safe without runtime guards.

### Horizon and probe

Primary horizon `H1` for evaluation and schema separation; `H2` for learned
selection or adaptation.

Probe: yes. Run a held-out BFCL-style subset through the real tool schemas and
record parse, execution, permission, and recovery outcomes separately.

### Evidence

Detailed facts, versions, and unresolved questions:
[`mechanism-notes.md#fr-05-tool-learning-and-function-calling-evaluation`](../landscape/papers/mechanism-notes.md#fr-05-tool-learning-and-function-calling-evaluation)

## FR-06: Model-Runtime Co-Design

### Core problem

Prompt order, tokenization, context replacement, retries, and provider caching
can change latency, cost, and reliability even when the semantic task is
unchanged.

### Current evidence

- PagedAttention manages KV-cache memory for serving throughput.
- SGLang uses RadixAttention for KV-cache reuse and structured-output execution.
- Prompt Cache treats reusable prompt modules as explicit cacheable units.
- Anthropic exposes provider prompt caching, and DeepSeek context caching is
  enabled by default with reported cache-hit/miss token fields.
- vLLM documents prefix hashing, cache isolation, and cache-salting concerns.
- Claude Code's architecture separates stable prompt-prefix context from
  per-request content; DeepSeek Harness persists the effective request context.

### Engineering readiness

High for prefix discipline, provider metrics, and adapter isolation; medium for
cross-provider scheduler-level optimization.

### Harness implication

The runtime should expose stable cache-key boundaries and collect cache hit,
miss, latency, and token-accounting data without coupling the core loop to one
provider implementation.

### Failure modes

- Dynamic timestamps or tool lists invalidate the prefix every turn.
- Cache reuse crosses trust boundaries or leaks inferred content.
- Provider cache hits are mistaken for correctness.
- Context replacement changes semantic content but not cache metadata.
- A runtime optimization assumes provider behavior that is only best-effort.

### Horizon and probe

Primary horizon `H1` for prefix discipline and metrics; `H2` for scheduler-level
co-design.

Probe: yes. Measure stable-prefix layout, cache hit/miss, latency, and cost
across two providers. Stop if the abstraction cannot preserve provider-specific
capabilities.

### Evidence

Detailed facts, versions, and unresolved questions:
[`mechanism-notes.md#fr-06-model-runtime-co-design`](../landscape/papers/mechanism-notes.md#fr-06-model-runtime-co-design)

## FR-07: Multi-Agent Orchestration

### Core problem

Multiple agents may isolate context, specialize tools, or parallelize work, but
coordination can also create new failure, security, and cost surfaces.

### Current evidence

- AutoGen provides a programmable multi-agent conversation framework.
- MAST analyzes 1,600+ annotated traces across seven frameworks and reports
  that multi-agent performance gains are often minimal.
- DeepSeek Harness exposes Agent/job primitives and independent session state;
  the inspected base does not establish that a multi-agent society is required.
- Claude Code contains subagent transcript and coordinator-context paths, but
  they are feature-gated and not a substitute for a measured orchestration
  design.

### Engineering readiness

Medium for a bounded parent/child task with isolated context; low for shared
memory and autonomous agent societies.

### Harness implication

If explored, start with a bounded child agent that has a narrow task, isolated
context, explicit tool permissions, a budget, and one structured result merged
by the parent. Do not start with shared mutable memory or autonomous
agent-to-agent organization.

### Failure modes

- Agents duplicate work or amplify one incorrect assumption.
- Parent and child diverge on repository state.
- Agents deadlock, recurse, or exceed cost budgets.
- Untrusted child output becomes trusted parent instruction.
- Parallel writes or commands violate ordering and safety assumptions.

### Horizon and probe

Primary horizon `H2` for bounded subagents; `H3` for autonomous societies.

Probe: only after P0, using a read-heavy or non-overlapping task with strict
budgets. Stop if it does not improve success/cost or increases unsafe effects.

### Evidence

Detailed facts, versions, and unresolved questions:
[`mechanism-notes.md#fr-07-multi-agent-orchestration`](../landscape/papers/mechanism-notes.md#fr-07-multi-agent-orchestration)

## FR-08: RSI and Self-Modification

### Core problem

A system that modifies its own runtime or policy may improve faster than manual
engineering, but it also changes the evaluator and the product under
measurement.

### Current evidence

- Darwin Godel Machine modifies its own code and validates candidate agents on
  coding benchmarks while maintaining an archive.
- Godel Agent dynamically modifies its own logic through runtime action.
- Both project implementations explicitly execute model-generated code and
  carry safety warnings.
- The inspected DeepSeek Harness profile/patch system supports human-composed
  activation, not autonomous self-modification.
- No shipped self-modifying runtime is established for Claude Code.

### Engineering readiness

Low for a production runtime; any credible study needs an offline isolation and
evaluation program first.

### Harness implication

RSI is not a next-step implementation. At most, study offline optimization with
a frozen benchmark, sealed evaluator, isolated execution, source snapshot,
human approval, and rollback.

### Failure modes

- Reward hacking or benchmark overfitting.
- The candidate modifies its own evaluator or reporting.
- A local gain causes an unrelated runtime or safety regression.
- Generated code escapes the sandbox or persists unreviewed.
- The archive rewards novelty without preserving maintenance quality.

### Horizon and probe

Primary horizon `H3`.

Probe: no runtime/product probe. Keep watch until the P0 release gate is passed
and a reproducible mechanism survives independent evaluation.
