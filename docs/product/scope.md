## 1. 产品定位与第一阶段目标

### 1.1 总体定位

> spool 是一个面向真实工作的自主 Agent 产品，以可靠交付为核心，以持续自主和自我进化为长期方向。

长期愿景是让 Agent 持续承担任务、解决实际问题并交付可信成果。人的介入集中于目标、授权和关键判断，而不是逐步指挥执行。RSI 是长期演进目标，不是已经具备的能力，也不是当前 P0 的实现要求。

总体定位、阶段目标、架构参考和实现原则分别表述，不把功能清单或参考产品名称当作 spool 的产品身份。

### 1.2 第一阶段目标与参考关系

以软件开发为首个落地领域，先做出一个可日常使用的通用 coding agent，建立和验证持续自主交付所需的基础能力。coding 是第一阶段的落地点，不是产品的最终边界。

对标 Claude Code 和 DeepSeek Harness，但不采用平等拼接的“双底座”：

| 基准 | 借鉴目标 | 不追求 |
|---|---|---|
| Claude Code：主要架构参考 | 编码执行主线、上下文与工具组织、用户控制、动态工作流与目标推进的公开行为 | 复制其源码、提示词、内部标识、历史包袱或品牌表达 |
| DeepSeek Harness：重点补充参考 | 自主任务编排、持久目标、完整可观测性，以及相关恢复和状态契约 | 直接采用其 runtime 作为底座，或复刻 Cordis、profile/bundle/patch 与全插件化架构 |

实现原则：最终产品代码独立实现，参考优先、理解后取舍；两个样本的优点需要适配到同一套 spool 架构中。

第一阶段的任务闭环目标：

> 用户可以在真实代码仓库中，通过自然语言完成“理解代码 -> 制定方案 -> 修改文件 -> 执行命令 -> 验证结果 -> 汇报变更”的完整任务，并且中断、恢复、权限控制和扩展能力都达到可产品化水平。

这不只是 demo、工具调用循环或 UI 壳。任务闭环、runtime 正确性和安全边界必须同时成立。

### 1.3 已确认的设计重点

- 自主任务编排：Agent 根据任务动态拆解、安排依赖、协调执行和汇总验证，不要求用户预先编写流程。
- 持久目标：目标及其进度、约束和完成证据不随一次回答结束而丢失；目标存续与自动继续的授权分开。
- 完整可观测性：目标、子任务、模型请求、工具动作、权限及验证证据可以关联和检查，不等于仅记录聊天文本。

这些是第一阶段架构必须考虑的方向，不等于三项完整产品能力都属于 P0 发布要求。不能将自主任务编排混同于已冻结的研究流程模板、流程市场或双层飞轮。

### 1.3.1 已确认的发布顺序

2026-09-19 用户明确确认：允许先对外交付基础 coding agent，持久目标、自主任务编排和完整可观测性分阶段补齐。此前“首版必须同时具备三项最小闭环”的建议不采用。

- 首个对外交付版本以本文 P0 为边界，满足验收后可以独立交付，不必等待 Goal 自动续轮、子 Agent 编排或完整图形化执行轨迹。
- “基础”不降低可靠性要求：权限、安全、取消、后台命令管理、会话恢复、上下文压缩、验证证据和本地执行审计仍是 P0。
- 首版支持模型在普通编码循环中制定和调整计划，但不因此要求结构化任务调度器或正式 Plan mode。
- 后续按依赖逐步补齐持久目标、有界自主任务编排及更完整的可观测性产品面；不另起一套执行内核。
- 本次批准的是交付顺序，不是绕过发布验收或立即上传、推送和发布的授权。

实施批次与验收映射见 [P0 实现计划](../architecture/p0-plan.md)。

### 1.4 与旧决策的冲突处理

旧版产品文档把“桌面端优先”和“流程飞轮 + 主动感知”作为核心交付。本基线依据最新开发决策覆盖其执行顺序：

| 项目 | 旧顺序 | 当前顺序 | 取舍 |
|---|---|---|---|
| 产品内核 | 先搭桌面 Agent 和流程系统 | 先完成通用 coding agent runtime 和任务闭环 | 延后桌面成品感，优先验证真正决定产品上限的 runtime |
| 主动感知与研究流程飞轮 | 第一版核心 | 冻结实现项 | 不影响对自主任务编排的架构设计，两者不是同一概念 |
| CLI/TUI | 仅作为技术底座 | P0 必交付验证面 | 与 headless 共用核心 runtime，最快暴露 loop、权限和恢复问题 |
| Desktop | 第一产品形态 | runtime 稳定后的首个完整产品 shell | 不取消桌面方向，但不在 P0 同时承担 runtime 和 UI 双风险 |

该顺序变化是对旧版开发计划的主动覆盖，不是文档之间尚未解决的冲突。

2026-09-19 的定位与架构讨论进一步明确：coding 是阶段目标；Claude Code 是主要架构参考；产品代码独立实现；RSI 保留为长期方向。此次同步不自动提升 P1 功能，也不把总体定位改回旧版研究产品。

## 2. 当前 P0 产品范围

P0 只包含让通用 coding agent 可以稳定工作所必需的能力。

### 2.1 核心任务闭环

- 交互式会话：持续接受用户输入并流式显示模型和工具执行过程。
- 单次执行模式：支持脚本、CI 或其他程序非交互调用。
- Agent loop：模型请求、工具调用、工具结果回填、停止条件和失败恢复。
- 多轮任务：能够基于同一会话继续处理后续请求。
- 中断与取消：用户可以终止当前模型请求和工具执行。
- 最终交付：明确列出改动、验证结果、剩余风险与未完成事项。

### 2.2 最小工具系统

- 文件和目录发现。
- 文件读取与范围读取。
- 精确编辑与新建文件。
- 内容搜索。
- Shell/Bash 命令执行。
- 后台任务启动、读取和终止。
- 工具执行结果截断和大输出落盘。
- Git 状态、diff 和测试命令的工作流支持，优先通过现有工具组合完成。

每个工具必须具有稳定 schema、明确错误语义、权限检查和可观察的调用结果。

### 2.3 安全与权限

- workspace 根目录边界。
- allow / ask / deny 三类权限决策。
- 危险命令和高风险文件操作识别。
- 对写入、删除、网络、提权和仓库破坏性操作实施分级授权。
- 用户选择能够持久化为可理解、可撤销的规则。
- 所有工具调用和权限决策可审计。
- sandbox 可以后置实现，但接口必须从第一天预留。

安全失败属于 P0 阻断，不作为体验问题延期。

### 2.4 会话与上下文

- 仅追加的会话记录，保证模型历史可以从持久事实重建。
- 会话退出后恢复。
- 中断和进程崩溃后的会话修复。
- 模型、上下文和工具结果的结构化记录。
- workspace instructions 和项目规则加载。
- 文件引用和必要上下文注入。
- 上下文压缩，并保留任务目标、已改内容、验证状态和未解决问题。

### 2.5 模型与运行环境抽象

- 模型适配器接口。
- 至少一个真实生产 provider。
- 至少一个 OpenAI-compatible provider 或明确的兼容适配路径。
- 配置、凭据和运行环境与核心 loop 解耦。
- 工具能力、系统提示和模型能力由组装层确定，不散落在业务代码中。

### 2.6 产品级交互质量

- 清晰的启动、工作区信任和配置流程。
- 流式输出、工具进度、diff/结果预览和错误展示。
- 用户可理解的任务状态，而不是内部事件流。
- 长任务支持计划、执行、验证三个可见阶段。
- 失败时给出可恢复动作，不静默失败或无限重试。
- macOS 为首要验证平台，安装和首次启动必须可复现。

### 2.7 扩展面

P0 至少提供一条稳定的第三方扩展路径。优先级如下：

1. 项目级命令或 skills。
2. Hooks。
3. MCP 或其他标准工具接入协议。
4. 自定义工具注册。

不需要同时完成全部路径，但架构必须允许追加扩展而无需修改 agent loop。

### 2.8 验收与发布

- 从干净环境安装并启动。
- 固定 benchmark 仓库任务能够完整执行。
- 功能任务、Bug 修复、重构和测试补全均有覆盖。
- 会话恢复、权限拒绝、工具失败、上下文压缩和大输出均进入验收用例。
- 发布前必须通过 typecheck、核心测试、端到端 coding task 和打包安装验证。
- 发布门槛必须基于实测结果确定，不用主观“感觉可用”代替数据。

P0 不承诺硬件断电 durability。进程崩溃恢复、事务前缀、WAL、`fullfsync` 和 artifact
同步仍须保留；真实断电、系统崩溃和存储控制器缓存丢失属于当前环境无法验证的
明确限制，按 DEC-044 豁免，release notes 必须披露。

## 3. P1 范围

只有在 P0 任务闭环稳定后才进入 P1：

- 持久目标及明确授权内的自动续轮。
- 结构化任务管理和 Agent 主导的有界自主编排。
- Plan mode。
- Worktree 隔离。
- Subagents 和后台 agent。
- 文件历史回滚。
- 更强的 sandbox 和跨平台隔离。
- Desktop 的完整产品 shell，以及 Web 或 IDE shell。
- JSON-RPC、Agent SDK、ACP 等自动化接口。
- 更丰富的工具结果 UI。
- 跨任务/子执行关联的完整轨迹视图；本地运行事实和权限审计不延后。
- 团队策略和企业配置。

P1 可以借鉴两个基准产品，但必须围绕通用 coding agent 的任务成功率、稳定性和开发效率立项。

## 4. 冻结的探索方向

以下内容暂时退出开发范围，只保留为研究记录，不进入当前路线图、不阻塞 P0：

- RSI 或自修改 runtime。
- 主动感知、自发发现任务和未获明确授权的后台自动推进；不包含 P1 已明确授权的 Goal 续轮。
- 研究流程模板和双层流程飞轮。
- 公共/私有流程模板推送机制。
- 流程市场、社区贡献和用户间分享。
- Agent Society、社交化多 Agent 和虚拟组织。
- 长期个性化记忆与用户画像优化。
- 面向研究、论文或通用知识工作的垂直产品化。
- 过早建设 Desktop、Web、移动端和 IDE 全平台矩阵。

冻结指暂不进入实现和发布验收，不等于从长期产品方向中删除。RSI 保留为长期方向；自主任务编排和持久目标属于已确认的架构设计重点，不因与“流程”“后台”用词相近而被一并排除。恢复冻结项的具体实现仍须在 coding agent 基础达到发布门槛后，经过独立价值验证。

## 5. 基准对标方式

对标必须落在可执行任务和产品门槛上，不做源码逐项克隆。

### 5.1 对 DeepSeek Harness

重点比较：

- runtime 是否能稳定完成多步任务。
- 会话是否可恢复、可追踪、可从持久记录重建。
- 工具、模型、权限和 sandbox 是否可替换。
- CLI、headless 和程序化调用是否共享同一核心 runtime。
- 新增能力是否能挂在扩展点，而不是修改主循环。
- 自主编排、目标状态和执行轨迹是否具有可独立验证的契约；不将参考实现的声明当作 spool 的运行证据。

### 5.2 对 Claude Code

重点比较：

- 在真实仓库中理解和修改代码的成功率。
- 工具选择、并行执行和失败恢复质量。
- 权限请求是否既安全又不打断正常开发。
- 上下文压缩后是否仍能继续任务。
- 会话交互、diff 展示和最终汇报是否足够清楚。
- commands、skills、hooks 和 MCP 等扩展是否实际可用。

### 5.3 固定基准任务

第一阶段建立 20 到 30 个小型、可复现的仓库任务，至少覆盖：

- 单文件 Bug 修复。
- 跨文件功能修改。
- 测试失败定位与修复。
- 重构且行为不变。
- 补充测试。
- 依赖或配置修复。
- Git 工作区安全操作。
- 长命令和后台任务。
- 会话中断后恢复。
- 权限拒绝后的合理绕行或停止。

每项任务记录：

- 是否完成。
- 自动测试是否通过。
- 是否修改了无关文件。
- 是否发生越权或危险操作。
- 人工质量评价。
- token、耗时和工具调用数。
- 中断恢复是否成功。

## 6. 新需求准入规则

任何新开发项必须同时回答：

1. 它是否提高 coding agent 的任务完成率、可靠性或安全性？
2. 它是否属于 P0，或确实被 P0 依赖？
3. 它是否有固定的产品入口、验收任务和可观察证据？
4. 不实现它，是否真的会阻断首个产品发布？
5. 它是否会重新引入已冻结的研究流程或平台化目标？

无法给出明确证据的探索性功能不进入当前主线。

## 7. 实施顺序

1. 固化 benchmark 任务、指标和参考行为。
2. 确定独立 runtime 架构，明确哪些接口借鉴，哪些实现自研。
3. 建立 agent loop、模型适配和最小工具的纵向闭环；第一条有副作用的任务就必须接入权限、执行意图持久化与取消。
4. 完善 sandbox 接口、会话恢复和异常路径，并验证安全承诺是否需要具体隔离后端。
5. 完成上下文压缩和产品级交互面。
6. 选择一条扩展路径并跑通第三方扩展。
7. 通过 benchmark、打包安装和安全验收后发布首个产品版本。

## 8. 参考代码边界

- DeepSeek Harness 用于机制、接口职责和失败场景研究；当前路线不直接依赖其 runtime、组装框架或搬运其业务实现。未来如要改变复用边界，必须单独决策并核对许可证、依赖义务和维护成本。
- `.references/claude-code` 是用于学习和行为分析的源码材料，不作为产品代码来源。实现时应采用 clean-room 行为对标，不复制其源码、提示词、内部标识或专有实现。
- 对标目标是能力与结果，不是项目结构相似度，也不是内部 API 相似度。
- “代码独立”不意味着禁止标准库和经确认的通用依赖，也不意味着为了独立而重新发明已经理解的设计原则。

## 9. 当前完成定义

当且仅当以下条件全部成立，首个“能对标”的版本才算完成：

- 用户能在真实仓库中稳定完成常见 coding tasks。
- 核心任务无需人工修复 runtime 或编辑内部状态。
- 中断、恢复、权限、上下文压缩和工具失败均经过验证。
- 至少一条扩展路径可由项目外部配置使用。
- 固定 benchmark 达到事先冻结的成功率、安全性和恢复门槛。
- 产品可以从干净环境安装并运行。

在此之前，不启动主动感知、RSI、流程飞轮或新的产品横向扩张。
