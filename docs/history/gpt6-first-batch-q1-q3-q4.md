## Q1：流程灵活性 vs 结构性

### 核心结论

1. 流程不应是 Agent 必须机械执行的脚本，而应是组织证据、检查遗漏和判断下一步的内部工作结构。
2. 公共流程提供质量基线，私有流程提供用户偏好和个性化；两者不是两条完整流程简单串联。
3. 结构的核心不是固定动作，而是结果必须具备的证据、判断和边界。
4. Agent 可以改变路径，但不能无理由丢失关键证据、质量判断和用户约束。
5. 流程是否成功，应由结果质量、证据完整性、异常处理和用户意图满足度判断，而不是由步骤执行率判断。

### 公共流程

公共流程应主要描述：

- 这类任务要解决的问题和完成条件。
- 关键结论应具备的证据类型。
- 必须检查的冲突、反例和不确定性。
- 需要重新定义问题、扩大搜索或停止交付的判断点。
- 失败后的重做、回退、局部复核和开放问题保留方式。

公共流程不应主要描述固定工具顺序或固定 Agent 角色链，否则容易退化为脚本。

### 私有流程

私有流程更适合被理解为用户逐渐形成的、可复用的工作偏好和判断习惯，而不是用户手工编排的复杂工作流。

用户可以自然地表达：

- 以后优先使用原始论文。
- 反驳部分必须单独列出。
- 证据不足时宁愿保守。
- 这类报告需要先给结论再展开。
- 这套偏好只适用于某一类研究。

Agent 负责观察、整理和适用这些偏好，但不应把一次性表达自动升级为永久规则。

### 公共与私有的共同执行

一次任务中：

1. Agent 识别任务目标和类型。
2. 选择相关公共质量基线。
3. 检索当前任务适用的私有偏好。
4. 判断公共要求与私有偏好是否冲突。
5. 根据任务生成临时执行路径。
6. 在证据变化、失败或新约束出现时调整路径。
7. 交付结果、必要的证据说明和不确定性，而不是展示复杂流程管理。

因此，公共流程定义底线，私有流程定义倾向，Agent 根据任务生成路径。

### 结构性与灵活性的边界

必须结构化：

- 目标是否被正确解释。
- 关键结论是否有证据。
- 证据与结论是否明显矛盾。
- 是否区分事实、推断和建议。
- 是否检查反例或反方证据。
- 是否暴露重要不确定性。
- 是否满足用户明确约束。
- 是否触发安全、权限或数据边界。

可以灵活：

- 搜索顺序和来源数量。
- 是否并行搜索。
- 是否先推理后查证。
- 是否拆分或合并子问题。
- 是否重复某一步。
- 是否使用一个或多个 Agent。
- 工具选择、停止时机和表达详细程度。

判断规则：

> 去掉某个元素会让结果无法验证、容易误导或违反用户边界，它就应成为质量要求；否则它更可能只是可替换的执行策略。

### Q1 验证方式

不测试“是否完整执行五个阶段”，而测试：

- 不同研究任务是否都能形成合理问题边界。
- Agent 是否能跳过无关步骤、重做失败部分和改变搜索策略。
- 关键结论是否稳定保留支持证据、反方证据和不确定性。
- 用户偏好是否被应用到适用任务，而没有污染其他任务。
- 相似任务的质量下限是否稳定，而不是依赖固定工具顺序。

## Q3：与现有范式和 Agent 产品的差异化

### 核心结论

1. “有流程”“有多 Agent”“能自然语言创建工作流”都不能单独构成差异化。
2. spool 的差异化应是：用户不需要设计流程，Agent 也不只是完成一次性任务，而是持续结合公共专业方法和用户个人工作方式。
3. 双层飞轮目前是护城河假设，不是已经成立的护城河。
4. 流程格式、角色设计和界面容易被复制；长期积累的质量评估、任务适配和用户偏好沉淀更难复制。
5. spool 的竞争单位不是“更强的单个 Agent”，而是“会逐渐适配用户、同时保留专业质量底线的研究工作系统”。

### 与 Agent 开发框架

LangChain、LangGraph、AutoGen、CrewAI、Swarm 等主要解决 Agent 构造、工具调用、状态传递、角色协作和执行编排问题。

spool 不应与它们竞争谁的编排能力更强，而应位于终端用户体验的更上层：

> 框架解决开发者如何构造 Agent；spool 解决普通用户如何获得一套逐渐适合自己的专业工作方式。

### 与工作流引擎

Temporal、Prefect 等擅长可靠执行、重试、恢复和长时间运行的确定性工作。

研究任务还包含目标变化、证据冲突、开放问题和不确定的完成条件。因此 spool 可以借鉴可靠执行和回放，但不能把研究过程降格为固定业务流程。

> 工作流引擎关注流程是否可靠地执行；spool 还必须判断下一步是否值得做，以及结论是否足够可信。

### 与专家流程和多 Agent 产品

MetaGPT 等方法强调预设专家角色和分工。spool 不应把“模拟专家团队”作为核心叙事。

研究任务中更重要的是：

- 是否找到相反证据。
- 是否存在竞争性解释。
- 是否识别结论的脆弱点。
- 是否知道何时停止扩展任务。

多 Agent 应围绕证据冲突和判断差异按需形成，而不是预先固定一组虚拟岗位。

### 与 n8n、Dify、Coze

n8n、Dify、Coze 已经覆盖工作流搭建、Agent、工具集成和部分自然语言生成工作流能力。

因此 spool 不能把“无代码创建工作流”当作差异化。区别应在于：

- 其他产品通常让用户搭建和管理显式工作流。
- spool 让用户表达目标，Agent 在后台形成和调整工作方式。
- 其他产品的核心资产是节点、连接器和应用配置。
- spool 第一版的核心资产是研究判断、证据质量和用户长期偏好。

### 与完整 Agent 产品

Codex、ChatGPT、Devin、Manus、TRAE 等产品已经覆盖对话入口、工具操作、长任务执行、过程展示和一定程度的自动化。

spool 不能仅以“也能调用工具”“也能长任务”“也能多 Agent”作为差异化。

spool 应逐渐掌握：

- 用户反复关注的问题。
- 用户认可或拒绝的证据类型。
- 用户常用的判断标准。
- 哪些未完成事项值得继续。
- 哪些结论需要复核。
- 用户最近的研究目标和上下文。

但主动性应优先表现为发现和建议，而不是无授权的持续后台行动。

### 双层飞轮的护城河判断

目前不能把以下内容本身称为护城河：

- 公共模板。
- 私有模板。
- 对话式创建流程。
- 团队更新推送。
- 多 Agent 调度。
- 简单版本管理。

潜在护城河来自三种复合积累：

1. 团队知道哪些研究输出容易出错、哪些反驳有效、哪些质量门值得保留。
2. 系统逐渐理解某个用户的研究偏好、适用范围和主动性边界。
3. 用户接受、修改、否定和重做结果形成反馈，反向改善公共质量基线。

双层飞轮只有在质量提升、返工减少、个性化沉淀和用户控制感都被真实验证后，才可能成为可持续护城河。

## Q4：目标用户画像

### 核心结论

1. 第一版优先服务有持续研究任务、但没有完整研究助理团队的个人研究者。
2. 最合适的早期用户不是完全不懂技术的大众，而是能判断结果质量、愿意持续使用、但不想自己搭建 Agent 系统的人。
3. 学术研究者最能验证公共质量基线和用户私有偏好的双层价值。
4. 研究生、独立研究者和技术型职场研究员最适合作为早期采用者。
5. 第一版应选择最深需求，入口保持自然语言和足够宽的任务表达能力。

### 推荐用户画像

核心用户是“���立研究型知识工作者”，包括：

- 硕士生、博士生。
- 需要持续查资料和写分析报告的研究人员。
- 技术型职场人士。
- 独立开发者或研究型创作者。
- 需要独立完成行业、技术或产品调研的人。

共同特征：

- 每周至少有一次中等复杂度研究任务。
- 任务通常持续多个回合。
- 结果需要被自己或他人审查。
- 不满足于流畅但不可追溯的总结。
- 不想自己维护复杂工作流。
- 能够对结果提出具体修改意见。
- 愿意让 Agent 记住部分工作偏好。

### 候选群体比较

| 用户群体 | 价值感知 | 使用频率 | 反馈质量 | 双层飞轮验证 |
|---|---:|---:|---:|---:|
| 学术研究者 | 高 | 中高 | 很高 | 很高 |
| 职场研究员 | 高 | 高 | 中高 | 高 |
| 独立创作者 | 中高 | 高 | 中 | 中 |
| 决策支持用户 | 很高 | 中 | 高 | 中高 |
| 日常用户 | 低到中 | 不稳定 | 低 | 低 |

### 推荐切入策略

以“研究型个人”定义核心用户，以“研究生和独立职场研究员”获取早期采用者：

- 学术研究者验证研究流程、可信标准和反驳能力。
- 职场研究员验证任务频率、主动建议和报告交付价值。
- 研究型创作者作为后续扩展场景，验证研究到内容的迁移。

普通大众暂不作为第一批核心用户，因为其任务复杂度和反馈质量差异过大，难以判断双层飞轮是否真正有效。

### 最广用户 vs 最深需求

选择“最深需求”，但保持宽入口：

- 用户仍然只需要用自然语言表达目标。
- 内部以研究流程作为公共质量基线。
- 早期重点验证技术调研、文献分析、问题综述和证据型报告。
- 后续再扩展到行业研究、创作者选题和决策支持。

## 统一产品原则

> spool 不卖流程、不卖多 Agent、不卖自动化节点；spool 提供一种会逐渐理解用户工作方式、同时保留专业质量底线的 Agent 工作系统。

内部关系：

- 公共流程：质量底线。
- 私有流程：用户适配。
- Agent：根据任务临时决定路径。
- 多 Agent：仅在确有分工价值时出现。
- 主动性：先发现和建议，再在授权后执行。
- 研究结果：包含结论、证据、反驳和不确定性。
- 用户体验：从目标和结果出发，不要求用户管理流程。

## 与既有决策的对齐

- 没有改变开源 Agent 软件定位。
- 没有改变桌面端优先。
- 没有改变双层飞轮。
- 没有把模型选择变成差异化。
- 没有引入流程市场或社区贡献机制。
- 没有让用户直接管理复杂 workflow。
- 没有把多 Agent 变成必须暴露给用户的功能。
- 没有把第一版扩展到多个场景。
- 保留 L3/L4 作为未来能力，但第一版不要求完整实现。

## 后续开放问题

1. 哪些质量要求必须成为硬门槛，哪些只能作为建议。
2. 公共流程与用户偏好冲突时，哪些情况必须提醒用户。
3. 如何判断用户偏好是长期有效，而不是一次性表达。
4. 主动建议的触发阈值如何控制，避免打扰。
5. 多 Agent 何时值得启用，如何判断收益超过额外成本。
6. 研究任务何时算暂时完成，何时应保留为待继续问题。
7. 用户需要看到多少“做了什么、依据是什么、哪里不确定”。
