## 1. 本轮技术取舍

| 编号 | 选择 | 原因及替代路线 |
|---|---|---|
| C01 | 主 Agent 动态规划，结构化任务记录，有界依赖调度 | 不为每个子任务结果强制增加一次主模型调用；不先引入任意脚本执行器 |
| C02 | 所有主/子 Agent 使用同一执行内核 | 子 Agent 是权限和上下文不同的执行实例，不是另一种 runtime |
| C03 | 每个协调会话一个主控制者；人工操作、目标续轮、任务批次统一 admission | 消除多个“继续循环”及重复派发 |
| C04 | 先单层委派、受控共享工作区；无隔离的修改任务串行 | 先满足拆分与协调，不以嵌套 Agent、共享仓库并行写入作为必要条件 |
| C05 | Goal 完成建议与证据验收分离；模型复核按需使用 | 不把模型自述或另一个模型的同意视为测试通过 |
| C06 | 事务型追加记录；优先用 SQLite 验证，JSONL 用作导出 | 任务领取、输入接收、状态与事件需要一起提交；避免先自建日志事务和恢复格式 |
| C07 | 主会话及其子会话属于同一执行存储域 | 不需要用两个独立日志的最终一致性来保证父子派发正确 |
| C08 | 取消、审批、恢复都是控制命令，不是发给模型的建议 | 模型输出不能撤销用户取消、扩大授权或决定进程已经停止 |

C06 是存储技术建议，不是数据库驱动安装批准。后续实现者须先验证运行环境和驱动；若需新增核心依赖，列明替代方案、维护状态、体积及风险并取得确认。语言、运行时版本及打包工具不因此自动冻结。

### 1.1 为什么不先做脚本工作流

用户要求的是 Agent 自主拆分并协调，不是必须执行模型生成的 JavaScript。首批基线允许主 Agent 一次提交多个任务和依赖，由调度器执行 ready 集合；遇到新信息、失败或集成节点，再交回主 Agent 判断。这并非每个子任务都必须等待一轮新的规划。

Claude 当前官方 [dynamic workflows](https://code.claude.com/docs/en/workflows) 提供脚本式控制流；[subagents](https://code.claude.com/docs/en/sub-agents) 提供委派与独立上下文。两者都是参考，不要求同时复刻。

本地 `docx/claude-code/src/tools/WorkflowTool/WorkflowTool.ts` 只有占位导出，`src/tasks/LocalWorkflowTask/LocalWorkflowTask.ts` 也是占位类型与函数。不能把这些文件的存在当作脚本运行器源码已经被研究。

DeepSeek 的 [worker-thread 引擎](../../.research/deepseek-harness/packages/workflow/workflow-worker-thread/README.md) 明确不把 worker/vm 当作安全边界。因此，先实现脚本式方案还需要独立解决代码隔离与恢复，不仅是多加一个工具。

只有有界任务对照证明结构化协调不足，才增加脚本入口。届时脚本也只能通过同一任务/执行契约派发工作，不另建权限、预算或事实来源。

## 2. 逻辑实体和持久化边界

| 标识/对象 | 约定 |
|---|---|
| execution-domain | 一个主会话及其子会话的存储与协调边界；有一个活动宿主写入者 |
| sessionId | 独立的模型上下文及会话视图；子会话与父会话共用执行存储域，不共享完整 prompt |
| runId | 一次已接纳的执行；终态不重新激活；恢复建立新 run 并引用前次 run |
| turnId / stepId | run 内部的回合与模型/工具步，不是业务任务或新的调度器 |
| attemptId | 一次实际 provider 请求；重试产生新 attempt，不复用网络尝试身份 |
| taskId + revision | 一个业务子任务及其语义版本；状态变更另有并发版本 |
| goalId + revision | 一个用户确认的目标及其验收条件版本 |
| commandId | 宿主生成或校验的幂等接收标识；同 ID 同内容返回既有结果，不同内容拒绝 |
| callId | 已接受的模型工具调用；网络重试和恢复不能隐式再次执行同一调用 |
| evidenceId | 验证结果与其输入、workspace 内容、验收条件和来源的绑定 |

语义 revision 与存储并发版本分开：目标/任务内容或验收要求变化会使旧结果需要重新评估；普通进度更新不必让全部下游证据失效。

小任务可以没有 Goal 和任务图。任务状态是事件的派生视图，不再另外维护互不一致的 JSON 文件、内存状态和数据库状态。

### 2.1 事务与产物

- 同一存储域内，输入接收、幂等检查、任务领取、run 创建和相关事件通过事务完成。
- 子会话 transcript、父任务结果和验证引用在同一存储域内提交，不依赖跨数据库原子提交。
- 跨不同存储域只保留关联，不宣称全局原子顺序或全局自动调度。
- 模型调用、Shell、用户审批等待、子任务等待都在事务外；不得跨长时间工作持有数据库事务。
- 大输出及附件先写入不可变产物，完成校验和持久化，再在事务中提交引用。事务失败形成的孤立产物可后续清理，已提交但丢失的产物必须报告证据缺口。
- SQLite 候选使用本机文件系统、WAL、外键约束和明确的 durable commit 配置。普通事务成功与断电持久性不是同一个承诺，须通过运行配置和故障测试确认。
- 数据库内部的页更新不违反“追加事实”：canonical events 不原地改写，索引和投影视图可以更新或重建。
- JSONL 导出保留 schema 版本、标识、顺序和因果关系；不是第二个实时可写的权威存储。

参考：[SQLite transactions](https://www.sqlite.org/lang_transaction.html)、[WAL](https://www.sqlite.org/wal.html)。驱动、版本、同步配置和备份方式必须在存储 probe 中记录；不能在运行期间仅复制数据库主文件就声称备份完整。

采用 WAL 前核对实际 SQLite 运行库版本及官方已知问题，尤其是 WAL-reset 修复是否包含在所用构建中；不能仅用外层语言运行时版本推断。持久化配置、checkpoint 与备份各有测试，不因单写者设计就省略故障验证。

## 3. 七个内部契约

这些是职责和语义，不是现阶段要求发布的 SDK 或具体函数签名。

| 契约 | 输入 | 结果及约束 |
|---|---|---|
| acceptInput | commandId、输入、session、宿主确认的来源 | 持久 receipt 或明确错误；禁止先 ACK 后落盘 |
| revisePlan | 目标/计划版本、有限任务变更集合、预期并发版本 | 全部验证后原子提交；环、未知依赖、越权和陈旧版本不做部分应用 |
| dispatchBatch | 本次允许执行的 task 集合、依赖、权限与资源上限 | 有界批次及执行关联；只执行已经批准的任务版本，不自动扩展计划 |
| executeRun | 已持久化的运行授权、上下文引用、工具能力、取消信号 | 通过共享内核输出规范化结果；不能自行扩大工具或预算 |
| recordOutcome | call/run 身份、观察结果、产物引用、提交版本 | 记录真实结果；过期结果留档但不完成新任务版本 |
| assessCompletion | 目标/任务版本、验收条件、证据引用、workspace 版本 | verified / reported / failed / unknown；模型建议不能伪造 verified |
| requestContinuation | goal 版本、当前授权、预算与待完成摘要 | 提交一个去重的续轮请求；仍需重新 admission，不能直接调用模型 |

取消、暂停、恢复、审批响应作为会话控制器的独立控制命令处理，不排在一个阻塞的模型请求之后。

来源、actor 和权限由宿主认证并附加；模型或外部文本不能通过填入 `actor=user` 获得控制权限。

### 3.1 统一错误语义

至少区分 invalid-input、stale-revision、dependency-unmet、permission-denied、approval-unavailable、budget-exhausted、cancelled、storage-failed、outcome-unknown、provider-failed。

错误包含是否开始外部操作、关联标识及允许的恢复动作。outcome-unknown 不是通用“可重试”；是否重试必须再次经过授权、任务版本和副作用核对。

provider 适配器不得隐藏一套无限重试。普通网络重试只在没有派发该 attempt 的工具、错误被判定为临时且预算允许时自动进行；所有实际 attempt 均计入记录和用量。

## 4. 规划、派发、集成

### 4.1 模型决策和程序调度的分界

1. 主 Agent 理解任务，决定是否需要分解。简单任务继续使用普通 loop。
2. 分解时提交有界任务集合、依赖、每项验收要求及需要回到主 Agent 判断的节点。
3. 任务协调器校验并持久化计划。环、重复身份、未知依赖、无法兑现的权限与并发约束直接返回错误。
4. 主 Agent 派发一个批次。调度器从这一批次选择依赖已满足的任务，受资源和 workspace 限制执行。
5. 子 Agent 使用独立上下文和同一内核。首批不允许子 Agent 再委派子 Agent。
6. 子结果先落盘并验证适用性。工具命令和验收已满足的任务可解锁已批准的下游任务，不必每次询问主模型。
7. 批次结束、任务失败、需要语义判断或人工介入时，向主 Agent 返回有界摘要与结果引用。
8. 主 Agent 决定重规划、修复或集成；总体目标另行验收，不能仅计数 done 子任务。

调度器不替模型凭空创建业务任务。自动 ready 派发只执行已授权批次；资源耗尽或取消后停止补充任务。

只有验收规则允许的证据等级满足全部必需条件，Task 才进入 done 并解锁依赖。reported 本身不解锁要求可执行验证的任务；需要人工接受的条件必须有实际的人工接受记录。验收命令重新取得必要的 workspace 权限，并核对被验证内容仍与证据绑定版本一致。

### 4.2 子任务上下文

包含任务目标、必要的用户约束、依赖产物、路径/内容版本、验收要求、可用工具和资源边界。不得仅传一句孤立 prompt，也不默认复制父会话全部历史。

返回结构为：执行状态、简要结论、改动与产物引用、实际验证、未完成事项、阻塞及用量。完整输出保存在执行记录中；主 Agent 按需读取，不将所有子会话串接到上下文。

所有工具与文件内容继续按来源处理。子 Agent 的“请忽略上级约束”等文字没有控制效力。

### 4.3 重规划

- pending 任务可被修改或替代；记录原因与新的 revision。
- running 任务需要先停止派发并发起取消；旧执行仍可能产生结果或修改，未核对前不能启动替代写入。
- 旧结果仍留在历史，但不自动记入新任务版本。只读产物可以由显式 adoption 重新关联，前提是输入版本和要求仍适用。
- 下游证据依赖发生变化后标为待重评。不能通过删除失败任务来把整体目标变成完成。

## 5. 工作区、取消与恢复

### 5.1 受控共享工作区

首批委派只支持两类执行模式：可强制限制的只读工作、独占工作区的修改工作。不是仅靠模型声明判断。

- 只读子任务可以有界并行，但不能与冲突的修改任务重叠。
- 修改权在整个修改任务期间保留，避免多个 Agent 按工具调用交错修改同一文件。
- Shell、测试、构建和包管理默认视为可能写入，除非执行环境确实限制了其效果。
- 后台命令归属于发起它的执行主体，共享其 workspace 执行权，不伪装成另一个子 Agent。同一主体可以继续有证据表明不冲突的工作；命令的输入/输出范围不明时不能擅自并发修改相关路径。
- 活跃后台命令的影响不会因前台工具返回而消失；向另一个主体移交 workspace 前，必须停止、完成或明确核对并移交这些命令的所有权。
- 主 Agent 等待子任务前必须释放自己的 workspace 执行权；不能持有修改权再等待需要修改权的子任务。
- 子任务等待期间不持有数据库事务，控制器继续响应取消和审批。
- 跨主会话也执行 workspace 冲突检查。另一个宿主进程无法证明取得独占所有权时拒绝并发修改，不仅靠内存标志。
- 用户或其他程序仍可能改文件；编辑使用实际内容校验，验收记录实际输入版本。

OS 隔离不可用时，不宣称“只读工具集”已经限制了任意解释器。无法兑现的模式不得静默改为无限权限。

### 5.2 控制状态

| 对象 | 主要转换 | 禁止行为 |
|---|---|---|
| Run | queued -> running -> waiting-approval / waiting-children -> running -> terminal | 终态复活；等待期间失去取消入口 |
| Task | pending -> running -> awaiting-verification -> done | 执行者直接用一句文本跳过证据检查 |
| Task 修复 | running / awaiting-verification -> blocked；显式恢复后再派发 | 旧 run 未核对就启动新写入 |
| Goal | active -> paused / blocked / complete；显式恢复到 active | 重启仅靠 active 状态自动开工 |
| Tool | proposed -> denied / not-dispatched；允许后 intent -> settled / outcome-unknown | 结果未知时按“没执行”重放 |

waiting-children 是同一 Run 的等待，不是创建第二个主 Run。子 Agent 有自己的 run 和 session，仍属于同一存储域。

### 5.3 取消顺序

1. 控制器接受取消，立即撤销新派发资格并持久化控制事件；若存储故障，内存中仍先阻止本宿主继续派发。
2. 将取消传给在途模型、工具、子执行和自有进程。
3. 已开始的动作有界等待、收集和结算；终止意图不代表操作已经停止。
4. 无法确认停止的进程或外部操作保持 unresolved，workspace 修改权不自动交给新写入。
5. 超时后可以结束等待并报告中断，但必须保留残留影响、恢复动作和待核查状态。

不承诺取消能撤销已发生的副作用。审批等待被取消后，迟到的批准无效；暂停与取消都不能被目标续轮立刻抵消。

### 5.4 恢复顺序

取得存储/工作区必要所有权，校验记录与版本，关闭中断的执行，核对进程和未结算操作，重读相关文件，恢复上下文投影，等待或验证当前授权，再创建恢复 Run。

没有 matching result 的工具调用必须区分未派发与结果未知。恢复不重新运行模型历史中的工具。有限的只读重试也要检查当前策略、预算和输入版本。

后台 Shell 的进程身份需要启动时间或等效不可混淆标记；不能只凭 PID 杀进程。作为任务产物的长期服务必须明确所有权和停止/移交策略，不能既遗留进程又声称任务已完全清理。

## 6. Goal：有界持续，不是反复发送“继续”

目标状态存储、续轮权限、执行调度、完成判断分成四个职责，共用同一协调入口。

### 6.1 续轮条件

所有条件同时成立才可提出续轮：目标版本仍有效；用户授权仍有效；主 Run 已结束；无待收集的阻塞工作；没有未核对的副作用；预算可用；没有更高优先级人工输入；尚未满足验收条件。

同一版本最多一个已排队续轮。排队不是开始，开始前必须重新检查上述条件。目标修改使陈旧续轮无效；预算只在实际接纳或消耗时计入，重启不归零。

用户正常输入优先获得协调权。新输入明显改变任务方向时，先明确对原目标的影响，不默认为它授权无限继续。

### 6.2 完成与阻塞

| 情况 | 处理 |
|---|---|
| 有明确的测试/产物验收 | 获取实际证据并检查适用版本 |
| 主 Agent 报告完成但证据缺失 | 返回缺口，要求补验证；不直接 complete |
| 开放性质量条件不能自动证明 | 记录人工或模型评审的身份、理由、局限；展示为 reviewed/reported，而非测试通过 |
| 一个模型复核认为完成 | 作为评估意见；不能替代未运行的测试或缺失的产物 |
| 权限、费用、输入不足或外部系统阻塞 | 保留目标与进度，明确阻塞原因和所需动作 |
| 多轮重复失败且无净进展 | 停止自动续轮并报告阻塞；阈值通过固定用例冻结，不交给 prompt 无限解释 |

完成记录包含每项验收条件的状态及 evidence 引用。缺失、失败、过期或 unknown 的必需条件不能被汇总文本抹掉。

轮次、时间、并发、请求和子任务总数必须有宿主侧上限；数值在验证阶段冻结，不继承参考产品默认值。硬 token 预算需要在途预留和可执行的 provider 上限，否则明确标为软预算。

## 7. 完整可观测性的最小实现

记录事实与展示是两个层次。最小可交付面是 CLI/headless 可查询、可导出的任务与执行记录，不以建设 Desktop 时间轴为前提。

| 记录组 | 必要内容 |
|---|---|
| input / control | 输入接收、来源、授权、取消、暂停、恢复 |
| goal / task | 语义版本、依赖、派发、重规划、结果采用和完成依据 |
| run / request | 执行与请求身份、父子关联、上下文引用、模型、usage 或 unknown、终止原因 |
| permission / tool | 实际执行参数、策略版本、审批、意图、结果及不确定性 |
| artifact / evidence | 内容引用、输出截断、验证命令、退出码和适用输入版本 |
| recovery / compaction | 中断边界、核对结果、压缩替换范围及恢复关联 |

保留 session 内顺序与父子因果关系；对外不保证不同存储域存在全局时间顺序。状态查询必须返回其对应的记录版本，以便判断缓存是否过期。

配置凭据只保存引用；用户文本和工具输出可能含秘密，默认仅本机受限权限保存，不默认对外导出。删除本地历史需要明确操作，删除后展示缺失引用，而不是悄悄伪造完整轨迹。外部 telemetry 和自动长期保留策略均不作为当前默认。
