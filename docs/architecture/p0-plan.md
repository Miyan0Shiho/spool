## 1. 本次发布决策

用户已确认允许先对外交付基础 coding agent，持久目标、自主任务编排和完整可观测性后续分阶段补齐。

P0 不是内部 demo：真实 coding 闭环、权限、取消、会话持久化与恢复、上下文压缩、本地审计、CLI/headless、项目扩展及安装验收仍必须成立。

不以 Goal 自动续轮、子 Agent、结构化任务图、脚本工作流、完整图形化轨迹、Desktop 或 RSI 作为首版发布前提。允许先交付不等于授权立即发布或绕过验收。

## 2. 首版的实际结构

| 实施单元 | 首版必须具备 | 首版不做 |
|---|---|---|
| 应用组装 | 配置、凭据引用、workspace 信任、模型与工具选择 | 全插件化、参考 runtime 依赖、热替换 |
| 会话控制 | 输入持久接收、排队、启动、取消、恢复、终态 | Goal driver、跨会话自主调度 |
| Agent 内核 | 模型请求、工具回填、显式重试、停止原因 | 子 Agent runtime、脚本执行器 |
| 上下文 | 项目规则、文件引用、模型投影、压缩 | 长期画像、跨用户记忆系统 |
| 工具与执行环境 | 文件/搜索/精确编辑、Shell、后台命令、授权、结果截断和落盘 | 任意第三方进程内插件、编排工具 |
| 持久记录 | session/run/request/tool/permission/verification 事实、产物、恢复 | 提前创建 Task/Goal 服务和空表 |
| 用户入口 | 流式 CLI 交互、headless、审批与错误、改动和验证报告 | Desktop、SDK/ACP 产品化、完整时间轴 UI |
| 项目扩展 | 声明式 commands/skills 的一条可用路径 | hooks/MCP 的并行全量建设 |

普通编码任务仍可让模型制定、展示和修订计划；这不要求正式 Plan mode 或任务图执行器。长命令的后台管理是 P0，不等于后台 Agent。

从第一天保留版本化记录、共享执行内核及明确模块职责即可。禁止用“为未来扩展”解释空配置、空服务、未启用的工具 schema 或另一套状态源。

### 2.1 P0 内部调用面

只需要实现执行契约的当前子集：

- `acceptInput`：持久接收、去重与输入身份。
- `executeRun`：在同一控制器下运行模型/工具循环。
- `recordOutcome`：记录模型、工具、进程及验证的实际结果。
- `assessCompletion` 的基础部分：汇报哪些检查实际运行、通过或失败；不建设 Goal evaluator。
- 取消、审批、恢复及记录查询：作为宿主控制入口，不能只能通过模型调用。

`revisePlan`、`dispatchBatch`、`requestContinuation` 暂不暴露，也不需要提前建空实现。数据库的格式版本支持日后增加相关记录；不借此承诺已支持目标或编排。

## 3. 实施批次

每批的退出条件是证据，不是文件数量。前一批失败时先定位原因，不通过扩大下一批功能掩盖缺口。

| 批次 | 工作与交付物 | 退出条件 | 不进入本批 |
|---|---|---|---|
| B0 基础验证 | 核验当前环境，选择可复现技术栈；存储、进程取消、安全执行和 provider 协议的有界 probe；依赖清单 | 选型有记录；必要安全边界可兑现；关键失败窗口有复现；新增核心依赖经确认 | 完整 UI、Goal、子 Agent |
| B1 运行与记录 | 输入/session/run 生命周期；事务事件记录与产物；确定性假 provider 驱动工具调用；恢复和取消 | 输入不丢失/重复；工具配对有效；存储失败阻止新副作用；假 provider 可注入失败 | 把 mock 通过当作真实任务通过 |
| B2 真实工具闭环 | 发现/读/搜索/编辑、新建、Shell、后台命令、权限、workspace 检查、截断/落盘 | 实际临时工作区的成功/拒绝/失败/取消/崩溃用例通过；用户无关修改保留 | 多 Agent 并行写入 |
| B3 真实模型闭环 | 至少一个真实 provider；兼容适配路径；用实际工具完成修复并运行测试 | 保存模型、配置、请求/工具记录和最终 diff；验证失败也被如实报告；规范化 provider 异常 | 单一 provider 字段泄漏进主循环 |
| B4 上下文与交互 | 规则加载、文件引用、压缩、CLI/headless、审批流程、结果报告、项目 skill | 压缩/恢复后继续真实任务；两入口共享权限与状态；外部项目配置能调用扩展 | 图形化完整轨迹、hooks/MCP 全家桶 |
| B5 验收与交付 | 27 项 fixture/evaluator 全部落地并执行；核心测试、打包、干净环境安装、发布报告 | 预先冻结的门槛满足；安全/恢复阻断项清零；失败、成本与限制可复查 | 因进度压力降低原有安全要求 |

fixture/evaluator 的实现从 B0/B1 开始随功能逐步增加，不拖到 B5 才发现核心行为无法测试。B5 是完整运行和发布判定，不是首次设计评价方式。

2026-09-19 用户确认当前环境不具备安全、可控的硬件断电测试条件，K01 的硬件断电
部分按 DEC-044 从 P0 发布门槛中豁免；进程崩溃恢复和 durable write 配置仍必须
验证并如实记录。

### 3.1 B0 要回答的问题

| 探针 | 需要记录的事实 | 不允许的捷径 |
|---|---|---|
| 存储 | SQLite 实际版本/驱动、事务和同步配置、单写者所有权、崩溃前缀、产物引用、备份恢复与 schema 升级 | 因为调用了 commit 就声称完成断电验证 |
| 进程 | macOS 的启动/取消、进程组、输出读取、后台身份及恢复核对 | 仅保存 PID 或假设取消信号意味着进程已退出 |
| 权限与隔离 | 文件/进程/网络各维度实际能限制什么、不可用时行为 | 用命令黑名单替代任意代码执行隔离 |
| provider | 文本流、完整 tool-call、结果回填、断流、取消、usage、错误及必要续传材料 | 固定一个样例响应、忽略 usage 缺失、隐藏重试 |
| 安装 | 首要平台的启动方式、运行时依赖、打包与第一次配置路径 | 用研究样本的 node_modules 或本机隐含工具证明干净安装 |

测试环境同时检查 fixture 所需命令、离线缓存、locale 和时区。环境不满足基准契约时报告 infra_error，不默默改变基准条件。

SQLite 是优先验证方案，不是已安装的核心依赖。若无法通过契约，先报告失败证据再修订；不要同时维护两个存储后端作为兜底。

执行本项目的模型身份不因此成为产品唯一 provider。不要把开发代理的模型身份硬编码到产品路由。

### 3.2 B1/B2 的边界

真实副作用从 B2 起进入受控临时工作区；在此之前用确定性测试实现复现失败窗口。接入真实写入时，权限、执行意图持久化和取消必须已经贯通，不能先做“可用工具”再补安全。

首版不得有 Goal/子 Agent 相关可见入口。主循环正常结束后停止，不因发现“可能还有事可做”自动发起新的目标轮次。

### 3.3 本地记录的首版可用程度

用户应能在终端或 headless 结果中查看：输入与运行状态、执行的工具/命令、审批和拒绝、改动、实际验证、失败与恢复边界。大输出有可读取的产物引用。

允许先采用文字视图和结构化本地导出，不要求复杂时间轴。关键事实必须来自记录，而不是根据最终聊天文本事后猜测。

原 `BENCH-FIXED-V1` 的 27 项规格保持不变。fixtures/evaluator 尚未实现，不允许填写推测的成功率。

### 4.3 环境与模型网络

fixture 工具执行按既有规格禁用网络，只有声明的 loopback 服务例外。真实模型调用应经工具执行域之外的 provider 通道；工具不能继承 provider 凭据或借该通道联网。

运行记录必须分别说明 provider 通道与 workspace 执行域的网络策略。若隔离环境无法同时满足约束，报告 infra_error 并修复基础设施，不静默放宽任务网络限制。

## 5. 发布判定

以下条件缺一不可：

1. 核心确定性测试、类型检查与当前 P0 架构用例通过。
2. 27 项固定任务全部执行并留下结果；失败、取消和 infra_error 都保留，不能跳过后只报告通过项。
3. 没有未解决的越权、用户工作丢失、凭据泄露、盲目重放副作用或关键状态丢失。基础设施错误不计成功。
4. 功能完成率、恢复率及成本等量化门槛，在独立校准后、正式候选版本评估前冻结。校准数据与正式结果分开；不能看到正式成绩后修改门槛。
5. 打包产物在干净环境安装启动，真实 provider、项目扩展、取消与恢复至少有可复查的安装后检查。
6. 发布说明如实标明已实现范围、支持环境和限制，不宣传尚未交付的 Goal、子 Agent 或 RSI。

当前没有运行数据，因此这里不编造成功率或成本阈值。B0-B5 的执行者负责产出校准与冻结记录；如果只有降低既定质量/安全要求才能发布，属于需要用户决策的产品取舍，不能自动放行。

## 6. 实现者交付与自主边界

每批至少记录：

- 改动范围与入口，新增依赖及其批准状态。
- 执行的验证命令、环境、退出结果及原始证据位置。
- 本批通过与未通过项，未解决风险及是否影响下一批。
- 相比设计的偏离、理由和复现依据。
- 下批输入与需要人处理的事项；没有用户决策需求就继续下一批。

实现者自主决定具体目录、内部命名、局部算法和测试组织；无需为这些细节反复询问用户。不得自动提交、推送、发布，不得清理用户或参考样本的未知改动。

需要用户参与的边界：扩大产品范围、改变已确认的独立实现路线、新增核心依赖、获得真实凭据/外部授权、执行破坏性操作，以及降低发布质量门槛。普通实现困难应先复现和调查，不直接升级成用户选择题。
