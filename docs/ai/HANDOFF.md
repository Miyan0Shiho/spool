## 分工与边界

- 当前代理负责前期设计；具体产品实现后续由 deepseek-v4.1-flash 承接。
- 最终代码独立，以 Claude Code 为主参考；DeepSeek 补充编排、持久目标、可观测性与可靠性契约。
- 不搬运参考项目源码、提示词；不直接依赖 DeepSeek runtime 或 Cordis。
- 不把候选契约当作运行成功，不把模型自述当作验收，不为满足单个场景叠加静默兜底。

## 本轮已收敛

- 主 Agent 动态规划，有限任务依赖调度，首批不增加任意脚本运行器。
- 主/子 Agent 共用执行内核；先单层委派、受控工作区写入。
- Goal 的持久状态、续轮权限、预算、验收分开。
- 记录是权威来源；优先验证 SQLite 事务型事件存储，JSONL 作为导出。
- 设计覆盖输入、任务领取、审批、取消、子任务晚返回、压缩、崩溃和证据过期。

这些属于整体设计基线，首版只实现 P0 实现计划列出的子集；A/K 的增强场景在对应能力启用前验证。没有新增数据库驱动或其他依赖；技术栈和依赖落地需在 probe 后确认。

## 已确认的发布顺序

用户已明确确认：先对外交付基础 coding agent，持久目标、自主任务编排和完整可观测性分阶段补齐。

此前“三项闭环一起完成后再首次发布”的建议不采用。首版仍必须具备安全、取消、后台命令、会话恢复、压缩、验证和本地执行审计；不要把它降为 demo。

## 下一步

后续实现者从 B0 开始，完成存储、provider、进程取消和安全执行的有界 probe，再逐批推进基础产品。按用户要求，只有产品或授权取舍需要其决策时才停止；具体文件组织与局部实现自行处理，修改契约必须给出失败证据和设计理由。
